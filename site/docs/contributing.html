Pull requests

Fixes, new commands, new apps, better docs: all welcome. This page is what to do from first clone to merge.

Before you start

  • For a bug, search the issues first. For a change that is more than a few lines or changes how something works, open an issue and describe it before you write the code.
  • Small pull requests are reviewed quickly. One change per pull request.

Set up

git clone https://github.com/Kalmai221/PythonOS
cd PythonOS
git switch -c fix-ping-timeout
python -m pip install -r requirements.txt
python main.py                          run PythonOS from the checkout

Python 3.9 or newer. PythonOS keeps its data (files/, .OSData/, users.json) in the folder you run it from; git ignores all of it. Fork the repository on GitHub if you cannot push to it.

The repository

commands/One file per command. Each has a config dict and an execute(args) function.
programs/Built-in programs started with run (the marketplace itself, for one).
core/Boot, shutdown, updates, hardware, recovery.
pyos/Libraries: file system, settings, shell variables, sandbox, manual pages, help.
online_packages/The marketplace apps and their catalog. See the Apps API.
OS_Export/Everything that builds the packages: Windows, Android, Linux, ISO, VM images, Docker, the Setup Wizard.
site_src/, site/The website. site_src is what you edit; site is generated from it (see below).
tools/Tests and checks.
shell.py, main.py, users.pyThe shell, the start-up and the accounts.

Rules

  • Match the code around yours. Same naming, same comment density, same style. A change should look like it was always there.
  • Python 3.9. No match, no X | Y in annotations that run at import. CI runs the tests on 3.9 and checks with vermin.
  • No new dependencies unless there is no other way. The core uses the standard library plus requirements.txt.
  • Work on every system. Windows, Linux and Android are all targets. Use os.path, do not assume / or a POSIX shell, and keep optional things (like a library) optional.
  • Running programs is reviewed. The live USB must never give a way out to the system underneath. tools/audit_lockdown.py fails on any new use of subprocess, os.system, eval and the like. If a change really needs one, add the file to ALLOWED in that script with the reason, and expect questions.
  • Say it plainly. Messages to the user are short, specific and say what to do next.
  • Line endings: the repository stores LF. Do not commit a file with its line endings rewritten.

Adding a command

A file in commands/:

from rich.console import Console

console = Console()
config = {"name": "hello", "description": "Say hello (hello [name])."}

def execute(args=None):
    console.print(f"Hello, {' '.join(args or []) or 'world'}!")
    return True

Then, all of these are required (the checks fail without them):

  • A manual page in pyos/manpages.py (cmd_page(...), next to the others).
  • A place in the help groups: add the name to CATEGORIES in pyos/helpview.py.
  • A line or two in tools/smoke_test.py (CHECKS): the command, text the output must contain, and the exit status.
  • A CHANGELOG.md line.

A command that only makes sense on some systems says so with "exports": ["iso"] in config. A command that reads files or piped input should use pyos/textcmd.py, which gives it the same errors and flags as the others. Return False (or a failing status) when it fails.

Changing the website or these docs

Edit the pages in site_src/, then run:

python tools/build_site.py

That writes site/. Commit both: CI runs build_site.py --check and fails if site/ is not what the sources produce. The command reference is generated from the manual, so to change it, change pyos/manpages.py.

Before you open the pull request

python tools/smoke_test.py         starts PythonOS and runs real commands; runs the tools/test_*.py files too
python tools/audit_lockdown.py     nothing new can run programs
python tools/check_docs.py         every command has a manual page and a help group
python tools/build_index.py        the catalog is current (commit the index files if it changed)
python tools/build_site.py         the website is current (if you touched it)

All of them must pass. CI runs more, including pylint, ruff and a Python 3.9 run: Tests and CI.

The pull request

A good description answers four questions. The pull request template asks them for you.

  • What changed, in a sentence.
  • Why: the problem, or the issue it closes (Closes #12).
  • How you checked: what you ran, and on which system.
  • What a user will see: new text, new commands, a changed default.

Commit messages say what the commit does, in the present tense (ping: time TCP connections). Add a line under the right heading of the newest section of CHANGELOG.md: ### PythonOS for the core, ### Exports for packages, ### Website, ### Development for tests and tools. See Changelog and releases.

After you open it

  1. GitHub runs the checks. Fix anything red; open the log of the failed step. A failure on only one system (Windows, macOS, Python 3.9) is a real problem on that system, not noise.
  2. A maintainer reviews. Expect questions about permissions, other systems and how it can break. Push more commits to the same branch to answer; there is no need to squash or reopen.
  3. When it is approved and green it is merged. Changes to PythonOS itself reach people with the next release. Apps and the website go live straight away.

Not sure whether something is wanted? Open an issue and ask. A short question costs less than a rejected pull request.
