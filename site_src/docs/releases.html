Changelog and releases

For maintainers, and for contributors who want to know where a change ends up.

Versions

A version is major.minor.patch (for example 1.0.9), set in config.json. A release is a git tag with a v in front, v1.0.9. Pushing the tag builds and publishes the release.

The changelog

CHANGELOG.md has one section per version, newest first. Each section is split by who gets the change (an app change is not a PythonOS change):

### PythonOSThe core: commands, the shell, the apps' runtime, settings. This is what updatecheck installs by itself and the only part PythonOS shows when it updates.
### AppsThe marketplace: new and changed apps. They go live as soon as the pull request is merged and are installed with pkg update all, so they are not part of a PythonOS update and are left out of what updatecheck shows.
### ExportsThe packages around the core: Windows, Android, Linux, the ISO and virtual machine images, Docker. A new download is needed to get these. PythonOS shows this part when it tells you a new package exists.
### WebsiteChanges to this site.
### DevelopmentTests, CI and tools. Not user-visible.

Ask which of those a change belongs to. A change to core_video.py is PythonOS; the same feature needing a different ISO start-up script is also an Exports line. A section written before 1.0.8 has no headings and counts as all PythonOS. python tools/test_changelog.py checks the format.

Write for the person who gets the change: what is different for them, in plain words, with the command name in backticks. Bullets are one or two sentences.

How a release is built

  1. The version in config.json and the section in CHANGELOG.md are set, and the Test workflow is green on main.
  2. Push the tag: git tag v1.0.9 && git push origin v1.0.9. The Build PythonOS workflow starts.
  3. A plan step decides what to build. An export whose inputs did not change since the previous release is not rebuilt: the release links to the old file. An export an earlier run of the same version already built is taken from that run, so after a fix only what failed is built again.
  4. The checks run, then the packages are built: Linux, Windows (installer, host, portable, Setup Wizard), Android (installer and apps), ISO (full and minimal, x86_64 and aarch64), virtual machine images, and the Docker image, which is smoke-tested.
  5. The release is published with the release notes (built from the changelog, one heading for each part), a table of which file is for which system, SHA256SUMS, a signature and build attestations. The core update (pythonos-core-<version>.zip and its manifest) is attached: this is what updatecheck downloads.

The manifest carries the PythonOS part of the changelog as its notes, and the Exports part as export_notes.

Tags

A tag is a promise about which commit users got, so avoid moving one after a release has been published. If a build fails before the release is published, fixing it and moving the tag is acceptable, and the plan step reuses everything already built.
