Apps API

An app is a folder with a data.json that describes it and a Python script that runs it. This page is the reference. Test and publish an app covers the workflow.

What an app is

Apps live in the repository under online_packages/<category>/<name>/. The folder holds at least two files. The catalog the store reads (online_packages/index-api*.json) is generated from these folders by tools/build_index.py, with a SHA-256 checksum for every file. PythonOS checks each file against its checksum before it installs it.

online_packages/utilities/habits/
  data.json        what the app is, what it needs, what it may do
  run.py           the program

A minimal app

data.json:

{
  "name": "Hello",
  "description": "Says hello.",
  "version": "1.0.0",
  "command": "hello",
  "scripts": { "run": "run.py" },
  "permissions": [],
  "categories": ["tools"],
  "lockdown_safe": true,
  "changelog": "First release."
}

run.py:

import sys

def execute(args=None):
    name = " ".join(args or []) or "world"
    print(f"Hello, {name}!")
    return True

if __name__ == "__main__":
    sys.exit(0 if execute(sys.argv[1:]) is not False else 1)

After it is installed, hello Ada (or run hello Ada) prints Hello, Ada!. The script is started as __main__ with the arguments after the command. It succeeds when it exits with 0. Keeping the logic in an execute(args) function, as above, lets you test it without starting a process.

Permissions

An app declares what it needs. PythonOS shows that before installing, records what the user allowed, and enforces it while the app runs: the app is started through a guard that refuses the matching calls.

PermissionLets the app
networkConnect to the internet and the local network.
filesRead and change the user's files and folders, with the same rules as the shell (a user cannot enter another user's home, and only administrators write outside their home and tmp).
notificationsShow notifications.
scheduleSchedule tasks to run later (alarms, reminders).
systemRead information about the computer (processes, memory, disk).
execStart other programs and run code on the computer.

Without files, an app can still use its own folder, files/tmp and the system temp folder. Without network, opening a connection raises PermissionError; without exec, so do subprocess and os.system. Ask for as little as you need: people read this list.

The guard stops an honest app doing more than it declared, and catches mistakes. It is not a barrier against deliberately hostile code. That is what review and the live-USB audit are for.

lockdown_safe

The live USB runs PythonOS as root with no way out to the system underneath. It only runs catalog apps marked lockdown_safe whose files still match their checksums. To be marked:

  • It may not ask for the exec permission or for Python libraries (pip).
  • Its code may not start processes (subprocess, os.system, os.popen, os.exec*, pty), evaluate code (eval, exec, compile, __import__), or import ctypes, code, pdb, cmd or telnetlib.

python tools/audit_lockdown.py checks every lockdown_safe app and fails the build if one breaks these rules.

Where an app keeps things

  • Per-user data: a small JSON file in the user's home, ~/.config/<name>.json, through pyos.appdata: appdata.load(name, default) and appdata.save(name, data). It is visible, easy to back up (backup) and private to each user.
  • Your own files: a folder you create inside the user's home (needs files). Existing apps write hidden files such as ~/.todo.json.
  • Settings: see below. The app never builds a settings screen.

An app that may also be run outside PythonOS should import pyos with a fallback:

try:
    from pyos import appdata
except ImportError:          # run on its own, outside PythonOS
    appdata = None

Settings

List the options in data.json. They appear under settings app <name> and in the Settings app. The app reads them with appsettings.get(package_id, key, default).

"settings": [
  {"key": "units", "label": "Units", "type": "choice", "choices": ["metric", "imperial"], "default": "metric"},
  {"key": "hints", "label": "Show hints", "type": "bool", "default": true},
  {"key": "seconds", "label": "Round length", "type": "int", "min": 10, "max": 300, "default": 60},
  {"key": "city", "label": "Home city", "type": "text", "default": ""}
]

Types are bool, int (optional min and max), choice (needs choices) and text. The default of every option is checked when the catalog is built.

Notifications

With the notifications permission: from pyos import notify, then notify.notify("Time is up", title="Timer", level="info"). The message is shown before the user's next prompt. level is info or warn.

No links

PythonOS is a command line system. An app cannot open a browser, and a clickable link means nothing in a terminal. When an app needs to point at a web address, print it as plain text and say that it is meant to be typed on another device. Do not use webbrowser, xdg-open or hyperlink escape codes.

Limits

Every app runs as a process of its own and is held to a memory and processor-time limit. The most specific wins: what the user set (limits set), then what the app declares, then the system default (a quarter of PythonOS's memory, setting app_memory_percent). 0 means no limit. An app over its memory limit is stopped with a message that says so.

"limits": {"memory_mb": 64, "cpu_seconds": 30}

API versions

The marketplace is versioned, so it can change without breaking systems that are already out there. An app says which API it is written for with "api": N (1 if missing). Each system asks for the catalog of its own version and refuses, with a clear message, an app that needs a newer one.

APIAdds
1The first marketplace: files, permissions, requires, settings.
2pip libraries, and run_<export> run files.

Stay on API 1 if the app needs no Python libraries, runs everywhere and rarely changes. Use API 2 only when you really need a library. Inside a running app, the environment variable PYOS_PACKAGE_API holds the API the app was written for.

Python libraries (API 2)

"api": 2,
"pip": ["yt-dlp", "miniaudio>=1.60"]

The marketplace installs the libraries when the app is installed, into the app's own .libs folder, and removes them with the app. The user sees them before agreeing. Rules:

  • Plain requirements only: a name with optional version limits (requests>=2.31). No addresses, paths or options.
  • Wheels only: nothing is built or run at install time. At most 20 libraries.
  • Not on the live USB and the virtual machine images, which cannot run apps with libraries. List the exports the app does work on (next section).

Which systems an app runs on

By default an app is assumed to run everywhere. If it does not, say so with exports, a list of windows, linux, android, iso (the bootable USB and the virtual machines):

"exports": ["windows", "linux"]

The catalog, pkg info and the App Library show it, and an app that does not fit the system is not offered there. The bootable USB is the baseline: an app must run on it, and build_index.py refuses an app that lists exports without iso. The one exception is an app that needs libraries (pip) or the exec permission, because the live USB cannot run those.

Run files for one export (API 2)

When a part of the app differs per system, give it a start file of its own:

"api": 2,
"scripts": {
  "run": "run.py",
  "run_windows": "run_windows.py",
  "run_iso": "run_iso.py"
}

PythonOS starts run_<export> for the export it is running in and run everywhere else. Without a run script there must be a run_<export> for every export the app lists. Each file must exist in the package; the catalog builder checks. The usual way is one run.py that imports the shared code, and thin run files that import platform-specific modules.
